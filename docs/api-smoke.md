# Public API smoke and performance checks

Run the registered public REST operations against a deployed environment:

```sh
bun run test:api:smoke --isolated-fixtures --output /tmp/holofolder-api-smoke.json
```

The runner needs the target project's Supabase admin environment (`NEXT_PUBLIC_SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `POSTGRES_URL_NON_POOLING` or `DATABASE_URL`). Use `bun --env-file=<file> scripts/api-smoke.ts ...` to select an environment explicitly. `--base-url` defaults to `https://app.holofolder.com/app/api/v1`. The API and database must belong to the same environment.

This is an opt-in integration check, separate from `bun test`. It creates two labelled synthetic accounts, grants temporary paid access, seeds 1,010 collection slots, and issues 30-minute API keys. It never uses a personal collection. It invokes real non-sold price providers for one card, asserts sold-comps and background-start API denials, and seeds then cancels an inert comparison job without starting a workflow. Production rate limits remain enabled; pacing happens outside measured request time.

All 71 current registered operations need an expected response and an explicit response assertion. The 56 admitted operations retain their existing functional checks, including the app-only job-start `403 ui_only` exception. The 15 staged native operations require an exact `503 native_operations_staged` denial, never a successful response. A new operation without coverage fails the suite. Additional checks exercise pagination beyond one page, full collection counts, stale-write conflicts, cross-owner denial, key revocation, and private artwork upload/download. Mutations use disposable state. Registry coverage concerns the REST transport and shared operation implementation; this does not exercise the MCP transport or OAuth browser flow.

Reads run once plus two repeats by default (`--repeats 0..5`). Writes run once. The report records HTTP status, assertion results, response bytes, full client latency and `Server-Timing` for auth, operation and total server duration. “First” means first observed in this run, not a forced cold start. Repeated server medians are compared to the 30 ms target. Provider-backed operations are labelled separately without that target. These small samples are smoke checks, not a load test or reliable tail-latency estimate.

The report keeps `operations[].verified` and performance metrics separate from `coverage[]`. Each coverage row has `successVerified`, `stagedDenialVerified` and one `coverage` classification: `successVerified`, `stagedDenialVerified` or `uncovered`. The final console event prints these counts and `nativeExecutionVerified: false`. A complete current run has 56 admitted checks verified and 15 staged denials verified, with zero uncovered. The existing job-start denial exception remains in the admitted count; it is not proof of a started job. All native operation summaries remain `verified: false`, with null latency medians and `targetMet: null`; denial samples retain their observed request times but never contribute to performance targets.

Exit 0 requires every admitted functional check, every staged denial assertion and completed cleanup. Missing operations, failed/missing assertions, unexpected 2xx, auth/schema errors or an incorrect staging error fail coverage. Functional/coverage/account-cleanup failures exit 1. Pending external artwork cleanup exits 2 only when all other gates pass. Unknown or failed cleanup never becomes success. Latency misses remain visible; `--strict-performance` also exits 1 for any measured non-provider median above 30 ms. Missing timing data still fails successful-operation verification.

Activity coverage removes a disposable fixture card, previews and applies its recovery, retries the exact apply request and verifies both directions of the linked history. The MCP HTTP/SDK integration regression in `tests/activity-mcp.test.ts` separately verifies tool discovery, preview/apply dispatch, mutation/idempotency hints, permission denial and revoked OAuth access with synthetic authentication. That regression is not a live OAuth browser-flow test.

Cleanup always runs after a failure. Accounts, namespace reservations and actor-specific rate budgets are removed. Private artwork cleanup also requires the real R2 credentials documented for the private artwork store. If those are unavailable, the runner reports the exact disposable object key in `cleanup.artwork` and exits 2. Delete only those keys from `holofolder-private-artwork` through the connected Cloudflare account and verify absence. Do not call that run clean until the pending list is empty. Reports contain fixture identifiers but never keys, signed URLs or response bodies. Preserve the report if a process is interrupted so remaining fixture identifiers can be cleaned up.

Sold-comps refreshes and background comparison starts are available only through the signed-in app. REST and MCP can read saved sold evidence, inspect/read/cancel jobs, and refresh eBay comparisons with explicit `source: "ebay"`. A sold source or omitted source on API refresh, and any API job start, returns `ui_only` (HTTP 403 on REST). These denials happen before provider or workflow calls.

For public API changes, run after the exact production deployment is ready and inspect every operation's verification and timing. Keep the report with the release evidence. Run focused unit/rollback checks before shipping; do not run this fixture-creating suite automatically on every unit test invocation.

## Price-check rate limits

The REST API's existing per-actor 60 reads / 20 writes per minute also covers sold-check reads and refresh requests. Main-app `/api/card-price-checks` and `/api/ebay/listings` share owner-account counters: 60 saved/listing reads and 20 refresh requests per minute. Partners share the owner's app allowance.

Actual upstream sold-comps requests have a global 10/minute budget; eBay listing searches have a global 60/minute budget. These Postgres counters apply across instances, accounts, REST/MCP operations and background jobs. They are fixed calendar-minute windows, separate from each card/finish/source's existing shared refresh claim and cooldown. Saved checks and cache hits never consume provider budget. They limit request rate, not monthly spend.

Exhausted limits return HTTP 429 and `Retry-After`; unavailable counters fail closed with 503. Background comparison jobs treat exhausted/unavailable budgets as retryable and use their existing two-minute backoff. Tests use synthetic counters and assert no upstream request follows a denial; do not exhaust shared production provider counters to smoke-test a 429.

## Staged native denial checks

`scripts/api-smoke-staged.ts` explicitly supplies strict, clearly synthetic inputs for all 15 current staged operations: five native reads, two preset operations and all eight POST storage contracts (`import_storage_arrangement`, `execute_slot_commands`, `execute_inventory_commands`, `create_storage_collection`, and recovery preview/apply v1/v2). Registry completeness and canonical schema validation happen before creating any accounts. A new operation, changed admission or missing/invalid input fails closed rather than silently skipping it. The inventory fixture covers the current 091 `insertAssign` schema with null selection; it creates no copy intent. No current private storage/planning evidence is fetched or guessed. Recovery event/token/revision values are explicit synthetic schema sentinels, not a reviewed or executable recovery plan.

The deployed runner sends these inputs through the real registry routes with the disposable account's authorized API key and requires the fixed denial status, exact error code/message and structured body with a request ID. All assertions finish before the sample is marked passed and the report is saved. This exercises denial coverage only. It proves no native read, write, SQL, recovery or latency acceptance. No native execution is authorized under #379.

Before the parent/operator runs the deployed suite, review the exact release head and verify it retains unconditional native admission denial. The inputs are schema-valid, so they are not a safety mechanism if admission has changed. Do not run this denial suite against an admitted or unknown build; retain synthetic-only evidence until the release boundary is verified. There is no admission bypass flag. The child implementation does not run hosted fixtures or change admission. Broader #376/#379 and project acceptance remain open.

Run `bun test tests/api-smoke-coverage.test.ts tests/api-performance-checks.test.ts` for fixture completeness, malformed/error-response rejection, coverage/exit semantics and actual local REST/MCP HTTP/SDK round trips. Synthetic auth/backend dependencies exercise all 15 inputs through the unmodified dispatcher/admission gate and assert zero executor or data RPCs. Existing native transport tests separately use subprocess-only module mocks to test future adapters; they are not hosted SQL/OAuth or enabled-feature proof. Native reads and revision-bound pagination have staged key/OAuth adapters with an explicit redacted developer projection. They remain behind fixed 503 admission and require hosted acceptance under #376/#379. Developer pages are not complete private planning snapshots or fresh-read ACK evidence; see `docs/native-developer-operations.md`.

## Release operator handoff

1. Parent verifies the exact deployed head, fixed native gate and matching API/database environment, then runs the isolated suite once after release review. Inspect `failures`, every coverage row, successful-operation timings and cleanup, not just the final count. Do not reuse previous fixture accounts or artwork.
2. Retain the original report and exit status. Let its `finally` cleanup finish. If interrupted, use only that run's `runId`, `cleanup.accountIds` and exact `cleanup.artwork` keys to identify disposable resources; verify the fixture metadata before account deletion.
3. If external artwork cleanup is pending, use the connected Cloudflare account to delete only those exact private-bucket keys. Verify each key is absent and the run's fixture-owner prefix is empty. Verify fixture accounts are absent too. Record the checks and cleanup evidence alongside the report; clear pending entries only after verified deletion. An external-cleanup annotation alone does not override pending/unknown runner state or turn the original exit into 0.
4. Parent owns deployed isolated smoke, external cleanup, acceptance and issue/project closure. These local tests and a PR do not complete release acceptance. This is an internal check, with no customer release or Framer announcement.

Terminal slot/inventory responses have a separate `assertTerminalStorageSmokeResponse` check, bound to the submitted operation ID and the strict declared error schema. An ordinary 409, accepted receipt or staged denial cannot pass it. Synthetic real-transport fixtures cover both terminal replay and unknown retry; these errors never count as successful operation/latency coverage. This adds no hosted smoke scenario or authorization to execute native commands.
