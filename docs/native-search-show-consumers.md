# Native search, card browser and Show consumers

Related: #374, #376, #379. Staged consumer composition only. Full issues remain open.

`lib/collection/native-card-consumers.ts` reuses Inventory's scoped distinct-copy projection. All storage includes Unassigned; a selected collection includes its placements only. Targets do not create inventory or explicit wants. Species metadata is nullable, including attested non-Pokémon printings. Printing badges count each item ID once and show both Owned and Wanted when applicable. A printing result is a catalog lookup, not a physical copy or a mutation destination.

Every explicit wanted entry keeps collectionId, slotId and wantedIndex plus inventoryRevision, collectionVersion, layoutRevision and slotVersion, the current account/owner/session and public expected wanted fields. Repeated identical entries in one slot or multiple slots remain separate. Recorded copy choices keep item ID and version, including identically graded copies. Choices use the complete owner Unassigned inventory even when the destination view is scoped to one collection. Their lookup labels contain no grade, certificate, holder or private artwork. Unknown language/catalog/finish remains unknown; a species target is never an exact printing.

The actual PokemonSearch, PokemonCardsBrowser, QuickMode, ShowHunt and QuickCardCheck components accept an optional `nativeConsumer: NativeConsumerBinding`. Absence preserves existing legacy behavior. Native binding suppresses legacy ownership actions, replacement/jump guesses, legacy Show purchase/bundle mutations and legacy offline preparation. Non-Pokémon lookups are not written into species-based recent-card history. Native Show purchase/bundle/offline-preparation adaptation remains a parent acceptance limit. Native hunt renders explicit destinations, including Trainers, and opens the existing price checker. Price checks retain the existing confidence, finish, freshness, manual refresh and billing rules. The new projection neither fetches nor invents provider evidence; no automatic paid refresh is introduced. Graded inventory value continues to belong to the existing Inventory/Analytics logic.

## Parent wiring, deliberately not implemented here

BinderApp and BrowserSession are reserved for integration and unchanged in this PR. The local consumer harness is not evidence that native production navigation is connected.

1. Extend `BrowserSurfaceBinding` with `nativeConsumer?: NativeConsumerBinding`. Compose it in the existing admitted BrowserSession render path from that render's `navigationScope`, `read`, and deliberately selected collection ID, or undefined for All storage. Carry the same complete/cached read used by Inventory. Never adapt the legacy species map into this prop.
2. Supply `editingAvailable` from the existing host editing predicate. `admit()` must check the live authentication/lifecycle, matching actor/owner/session, online state, current complete read, queue readiness/pending work and unresolved recovery, using the existing admission checks. Return null on any failure. On success return the current scope/read, a newly created original app `OperationIntentContext`, and the existing `SlotCommandSink` (`receive`). Do not snapshot an old closure as authority. Cached startup always supplies editingAvailable false and a denying admit function.
3. Supply `openCard(card)` as an exact-printing lookup callback to the existing card-detail browser, including cards with no species ID (`PokemonCardsBrowser` accepts `pokemon: null` with native exact `cardDetails`, seeds that printing and does not issue a species query). It must not resolve a slot by species or write collection data. Forward this binding to the existing PokemonSearch/search-overlay, PokemonCardsBrowser and QuickMode invocations. QuickMode passes it to ShowHunt and QuickCardCheck. Keep it absent in legacy-authority flows. Reset/close consumer UI on host account/session changes as with the existing pickers.
4. Do not add a queue, new sender, API endpoint or native-admission switch. The existing sink owns durable local acceptance, unknown outcomes, fresh-read ACK and replay. Only a returned `saved-on-device` acceptance permits that message; a void draft callback explicitly says it is not confirmed saved.

At click time, `prepareNativeWant` re-resolves the exact chosen entry under live admission and requires the captured versions/session and public fields still match. It requires a separately chosen existing copy or explicit new raw copy, rejects occupied/incompatible targets and delegates to `prepareSlotPickerIntent` with `occupied: cancel`. No automatic first match, species/printing collapse, legacy collection write or replacement occurs.

The optimistic sink rejects server-only `expectedPublic` patches. Its existing first-party complete read retains the actual full wanted entry, so this helper passes that exact unchanged entry as `fulfillWant.expected`, with the chosen index and version fences. It never reconstructs attribution/image fields from lookup labels or redacted REST/MCP payloads. The parent must use the existing private first-party read authority, not a public DTO. The public REST/MCP private-preserving contract is unchanged.

## API, help and evidence boundary

This is device-only presentation and composition of existing complete/cached owner reads with `execute_inventory_commands`' existing first-party assign path. Session lifetime, local copy/destination choice and the local command sink have no new server resource or API operation. Registry, permissions, OpenAPI and public error contracts remain unchanged. Public native inventory/slot/creation admission remains fixed 503. No new event is fabricated for looking at, choosing or preparing a destination; actual execution owns transactional audit attribution.

The loopback-only `/app/e2e-harness/native-card-consumers` mounts the real components, complete-read validator, projection and slot command planner. Its read data, admission and draft sink are synthetic. It asserts precise draft contents and refusal behavior; it does not claim BrowserSession, IndexedDB durability, HTTP execution, server acceptance, production binding or physical-device proof. Six phone browser/standalone emulation profiles cover the affected actual components only. The true offline lookup case opens the existing lazy checker online before disconnecting; it proves reopening loaded code with synthetic cached evidence, not first-use offline loading, service-worker preparation or offline startup binding. No full e2e, hosted access, SQL or publication.
