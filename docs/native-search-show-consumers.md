# Native search, card browser and Show consumers

Related: #374, #376, #379. Staged consumer composition only. Full issues remain open.

`lib/collection/native-card-consumers.ts` reuses Inventory's scoped distinct-copy projection. All storage includes Unassigned; a selected collection includes its placements only. Targets do not create inventory or explicit wants. Species metadata is nullable, including attested non-Pokémon printings. Printing badges count each item ID once and show both Owned and Wanted when applicable. A printing result is a catalog lookup, not a physical copy or a mutation destination.

Every explicit wanted entry keeps collectionId, slotId and wantedIndex plus inventoryRevision, collectionVersion, layoutRevision and slotVersion, the current account/owner/session and public expected wanted fields. Repeated identical entries in one slot or multiple slots remain separate. Recorded copy choices keep item ID and version, including identically graded copies. Choices use the complete owner Unassigned inventory even when the destination view is scoped to one collection. Their lookup labels contain no grade, certificate, holder or private artwork. Unknown language/catalog/finish remains unknown; a species target is never an exact printing.

The actual PokemonSearch, PokemonCardsBrowser, QuickMode, ShowHunt and QuickCardCheck components accept an optional `nativeConsumer: NativeConsumerBinding`. Absence preserves existing legacy behavior. Native binding suppresses legacy ownership actions, replacement/jump guesses, legacy Show purchase/bundle mutations and legacy offline preparation. Non-Pokémon lookups are not written into species-based recent-card history. Native Show purchase recording and offline preparation remain parent acceptance limits. Native hunt renders explicit destinations, including Trainers, and opens the existing price checker. Saved price checks retain the existing confidence, finish, freshness and billing rules; native comparison exposes no paid refresh control. The new projection neither fetches nor invents provider evidence; no automatic paid refresh is introduced. Graded inventory value continues to belong to the existing Inventory/Analytics logic.

## Actual host wiring

The admitted BrowserSession now supplies the same current complete/cached scoped read used by Inventory, with an explicit current-collection filter or All storage. BinderApp completes the binding with an exact-printing lookup callback and forwards it through Search, PokemonCardsBrowser and QuickMode. Exact non-Pokémon lookup has separate card state and opens with `pokemon:null`; no species destination is invented. The existing legacy species browser remains unchanged when native binding is absent.

The admission function is refreshed after each committed host render and checks live authentication/lifecycle, online state, complete current read, pending/legacy/recovery state and active refresh/send work. It returns current scope, original app operation context and the existing durable command sink. That sink re-reads canonical IDB and applies existing CAS/queue admission before durable handoff. Cached startup supplies its real saved read with editing disabled and an admission function that always denies. Session/account teardown unmounts the scoped host and its lookup UI; invalid or stale callbacks cannot acquire authority. No new queue, sender, endpoint, native-admission flag or legacy write path is added.

Lookup data is composed from the existing card cache plus the host's current catalog evidence, so cached cards are not replaced by the empty legacy species map. Native price-check ownership actions use native admission while legacy purchase and offline-preparation actions remain disabled.

At click time, `prepareNativeWant` re-resolves the exact chosen entry under live admission and requires the captured versions/session and public fields still match. It requires a separately chosen existing copy or explicit new raw copy, rejects occupied/incompatible targets and delegates to `prepareSlotPickerIntent` with `occupied: cancel`. No automatic first match, species/printing collapse, legacy collection write or replacement occurs.

The optimistic sink rejects server-only `expectedPublic` patches. Its existing first-party complete read retains the actual full wanted entry, so this helper passes that exact unchanged entry as `fulfillWant.expected`, with the chosen index and version fences. It never reconstructs attribution/image fields from lookup labels or redacted REST/MCP payloads. The parent must use the existing private first-party read authority, not a public DTO. The public REST/MCP private-preserving contract is unchanged.

## Read-only Show bundle comparison (#374)

Native Show now exposes the existing Bundle comparison. Choose an exact catalog printing and finish in the checker, then tap Bundle. Each tap adds one selected entry, including repeated printings; removing an entry removes only that occurrence. These are offer quantities, not physical inventory IDs or inferred destinations. Native labels use the current scoped projection, including simultaneous Owned/Wanted counts, No exact saved match and Ownership unavailable. Selected-collection scope and partner owner/account/session scope stay with the existing host binding. Targets never create ownership or wants.

Native selections live only in the mounted Quick mode, without reading or writing the legacy session bundle. The comparison uses saved exact-finish catalogue evidence at high/medium confidence and already-saved qualified sold evidence under existing access/freshness rules. Headline-only, missing, non-finite, zero/negative or unmatched finish prices stay unknown. Grade/certificate value is never inferred from a printing quote. The selected references retain their currency and known FX evidence; mixed currencies or any unpriced entry suppress the bundle verdict and price scale, with an explicit incomplete-evidence message. The subtotal still identifies coverage. No guessed FX or partial-total buy recommendation. Legacy bundles retain their existing partial-price behavior.

Native Bundle has no paid check/refresh, purchase recording, acquisition, replacement, budget, or offline-preparation action. Native card comparison reads saved provider checks without exposing paid refresh controls. Cached inventory is labelled read-only; loaded checker and bundle code and saved references can be reused after going offline. This does not prove first-use offline chunk loading or preparation. The existing Quick mode overlay owns close, Escape, back and backdrop handling; its existing swipe primitive also dismisses an open native bundle.

No new REST/MCP operation, registry or OpenAPI change: this is composed device pricing over existing reads. Production native admission remains false/503. Purchase/preparation parity, hosted rollout, parent review/merge/deployment and whole-issue acceptance remain open.

Parent review found saved sold checks bypassing unknown-language and unsupported-finish gates. Native comparison now requires known English plus an established normal/holo/reverse-holo finish before it reads or accepts saved sold evidence. Exact catalogue references require matching card/language/finish/standard variant, a known source, high/medium confidence and a valid nonfuture provider date. Nested finish rows with missing identity are excluded before the general legacy normalizer can supply defaults. Bundle entries retain minimal quote provenance and recheck it every minute and on focus/visibility: over-seven-day confidence caps at medium, over-30-day or unknown-date quotes become unpriced, and native amounts never fall back to legacy retained numbers. Legacy behavior remains on the existing default path.

## Show Hunting list on native (parity)

Show mode's Hunting list is the same grouped list as before native: the want list by Pokémon with sort, era/set/illustrator filters, pay-up-to prices, Good pickups and Check comps. `nativeHuntItems` builds its source from the current native read (`nativeCardConsumers` wants), one item per species, plus a "Trainers & Energy" group for wanted printings with no species. Native has no species-only "any card" wants, so those groups no longer appear. Tapping a card opens the existing deal check, which still shows the exact wanted entries (and their fill action) for that printing. Pay-up-to only appears for high or medium confidence quotes. The list reads the device price cache, so it keeps its prices offline.

## Show purchase tally on native (parity)

Native Show records purchases again. In Show mode, Bought in the deal check logs the asking price, and Bought bundle in the bundle logs its total split across the cards by market price (evenly when no card is priced), under one bundle ID. Both show a confirmation with Undo. Bought also adds each card to the collection as one new raw copy with the bought finish and language (when known), through one native inventory edit on the device queue (`lib/collection/show-bought.ts`, `hooks/use-show-bought.ts`), so it works offline. A copy goes into the first empty pocket wanting that exact printing, filling that want; a pocket holding any copy is never chosen. Otherwise the copy is added unassigned. The confirmation says where ("Added to Page 3 · Pocket 4" or "Added to your inventory"). Undo queues a linked pair, removing the new copies and then restoring the filled wants, and takes the purchases off the tally; copies moved or removed since are left alone. The tally only gets the purchases once the cards are saved on the device. Bought plans on the read the device shows, queued edits included, through its own admission (`acquire`), separate from the online-only lookup admission. Purchases are queued on the device (`lib/show-purchase-sync.ts`) and pushed to `public.show_purchases` when online, idempotent on `owner_user_id,client_id`, then the current show's purchases are pulled back, so the header tally works offline and a partner sees the same tally. Bought is available whenever the signed-in owner or partner is in their own binders, including offline and while native editing is unavailable; shared views never see or write a tally. The REST/MCP `list_show_purchases`, `add_show_purchase` and `remove_show_purchase` operations write the same rows.
