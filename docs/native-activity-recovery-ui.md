# Native Activity recovery preparation (#396)

This slice stages the existing native recovery engine behind the native browser session. **It is not enabled in production.** `/app/api/native-recovery` always returns private/no-store `503 native_operations_staged`; slot/inventory and developer admission remain closed. The existing local-only, nonhosted inventory harness alone injects synthetic clients into the real authenticated bridge. The original UI slice added no SQL. The additive 092 terminal contract below introduces one private migration, with no grants, conversions, admission switches or hosted commands.

Legacy Activity/087 Undo remains unchanged in legacy collection views. The native host never sends a native event through `collection_recovery_v1`. Its explicitly recognized events are `slots.create/move/clear/remove/update/bulk`, `inventory.add/edit/patchGrading/removeOwned/unassign/assign/move/removeSlots/deleteCollection/bulk`, `collection.create` and linked `recovery.apply`, with format-1 native entity changes. Recognition only offers review; the private engine decides support, conflicts, allowances and current authorization. Unknown events have an explicit unavailable explanation.

## Review and original intent

Activity uses the existing scoped safe history read, what/who/when presentation, pagination, original-entry links and shared dismissible sheet. Opening a native preview requires a newly authorized complete first-party owner read and an online session. Only sanitized descriptive changes and named conflict reasons return from the existing recovery registry/bridge. Neither raw `recovery_state`, command evidence, inverse SQL, certificates nor private artwork enters the new preview/history projection. No developer read is treated as complete private first-party evidence.

Removed ownership offers an explicit per-copy **Restore as Unassigned** choice using `restoreUnassignedItemIds`; it never manufactures another copy or chooses acquisition/placement. Default creation requires an explicit nominated native replacement. Its v2 preview includes exactly the current inventory revision and nominated collection version/layout precondition. No replacement is preselected. SQL revalidates every choice; conflicts never expose a usable confirmation token. `private_assets_unverifiable` remains unavailable under the existing engine and #390, with no asset bypass. Cancel is available only before confirmation.

The authoritative native request parser is shared by the server bridge and browser persistence. Preview/application versions remain separate, strict and byte-compatible with existing requests. Existing public recovery inputs and accepted receipts are unchanged. The additive 092 error schemas and generated OpenAPI below declare recovery-specific terminal outcomes, with unconditional staged admission preserved. Preset discovery/preview changes from #466 are independent and must be preserved during integration.

## One durable queue

Confirmed recovery extends the **existing** atomic `slot-intent:v1` IndexedDB record with an optional `recovery` list. Old records remain readable. There is no separate database/store, localStorage request shadow, optimistic restore or alternate recovery ledger. The original account, owner and device recipient are the record's scope; the immutable request retains event ID, operation ID, reviewed token, version, Unassigned choices, exact replacement preconditions and original device/time context. Server actor/source/membership still come only from authentication, never that device context.

Confirmation awaits the IDB commit before UI acknowledgment or apply. Outstanding slot/inventory work blocks new recovery; unresolved recovery blocks new slot/inventory work. A lease fences concurrent tabs and late replies. Every error, unclassified 409, timeout, expiry, billing/access refusal and lost reply retains the original exact request. 089 proof remains limited to slot/inventory commands. The additive 092 contract below supports explicit discard and a separately reviewed new native recovery only after a committed recovery-specific terminal proof. Unknown requests remain retained indefinitely until exact retry resolves them.

An accepted receipt is saved before attempting verification. It is historical acceptance, never a current snapshot. ACK requires a separate all-stream complete read started after the matching reply, current actor/owner/JWT-session/membership epoch, the retained lease and an inventory revision at least as new as both the receipt and saved base. Reload can resume a failed verification from its saved receipt without applying again. An unknown result requires explicit **Retry exact recovery**, not a status guess. Successful verification installs current state, including newer unrelated edits, and preserves the original immutable intent/receipt locally. Scope teardown ignores late work and leaves the original account/device queue untouched; another account cannot replay it.

## Terminal noncommit (092)

Prepared only, public admission remains unconditional 503. Migration 092 extends the existing recovery apply v1/v2 gateway and `recovery_v1` lifetime ledger, preserving the exact original owner/request/trusted-intent digest. Version selects the original engine; a mismatched operation/version cannot borrow its receipt. Current authenticated actor, source/client and live membership/billing checks still precede replay. Accepted and rejected receipts are looked up before mutable private plan reconstruction, so later edits or inverse recovery cannot change a historical receipt.

The private helper upgrades membership locks to SHARE, re-resolves owner after waiting, and retains management6102 then root4701 locks outside the inner apply subtransaction. Only explicit `recovery_plan_conflict` and `recovery_dependency_conflict` engine predicates carry the dedicated HF092 state. Only these, after complete inner rollback, may append a four-field terminal result to the same ledger. An arbitrary 40001, even carrying the same message, is not proof. Invalid requests, collision, missing events, unsupported assets, billing/auth errors, recorder/deferred failures, SQL cancellation and lost network replies remain unknown. All fresh plan reads, frozen mapping checks, explicit default replacement, 090 private fields and 091 insertAssign remain unchanged. No private inverse/evidence/certificates/assets/current rows are returned.

The first-party apply bridge returns private/no-store status 409 with exactly `{version:1,operation,operationId,rejection:{outcome:"rejected",operationId,code,inventoryRevision}}`. The browser validates both IDs, operation/version, content type, headers and strict known proof fields in the live session. Public REST uses `storage_recovery_rejected` and `error.rejection`; MCP uses the identical structured error with `isError:true`. Error schemas are registered on native apply v1/v2, separately from accepted receipt schemas, and exported in generated OpenAPI, Markdown/LLM reference and MCP error metadata. Legacy 087 Undo is unchanged.

The existing optional `recovery` list stores this proof atomically beside the immutable original intent. It does not store a second request or optimistic inverse. Proof is persisted before a newly started all-stream complete owner/session read. Failed reads, reload, teardown and concurrent leases retain the original/proof. The review UI explicitly says **Recovery did not commit** and offers **Refresh current storage**, then **Discard noncommitted recovery**. Discard itself obtains another fresh complete read and atomically checks proof, intent, lease, scope and revision. It preserves the original/proof and records `resolution:"discarded"`, with `receipt:null` and `synchronized:false`. This truthful distinct state clears the unresolved queue gate for scanner, grading, bulk fill and ordinary commands. Old records without proof/resolution remain compatible and unresolved.

Only after discard may the user choose **Review new recovery**, obtain a new preview and explicitly confirm a new operation ID. Accepted receipts and unknown results never gain discard/rebase. The parent's original first-confirmation identity remains frozen through IDB abort retries. No recovery token is automatically refreshed or replayed under a replacement ID.
