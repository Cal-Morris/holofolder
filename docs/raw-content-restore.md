## One supported reconciliation path

A collection-scoped v2 file can reconcile **one existing native raw collection** with **the identical ordered stable slot IDs**, the exact unchanged copied manifest and exact unchanged canonical per-slot origins. Edited copied targets and appended null-origin slots are allowed within the envelope. Its name/kind/presentation/location and grid must match the trusted current read. New planning emits command version 2: at most 1,025 slots and manifest entries, 2,050 distinct current/desired raw-copy refs, 100 wants per slot, 8,192 work units (`2S+I+W`) and 4 MiB command/JSONB text. The parser budgets PostgreSQL separator spaces as well as compact UTF-8 bytes. These provisional bounds are not a production full-Dex support claim. Persisted version 1 keeps its original 256/512/1,024/1-MiB envelope, null origins and null/empty Blank manifest, without rewriting commands or proofs. The existing audit 16,384-entity/16-MiB bounds and 10-second SQL deadline still apply. No truncation, batching or partial restore.

The plan replaces each explicitly selected slot's target/status/wants and restores exact existing raw copy placements within that collection or from Unassigned. Every displaced current copy needs explicit `releaseItemIds` consent and remains owned in Unassigned. A copy already placed in another collection blocks the entire plan. Item/slot/collection IDs stay unchanged; item rows, identities and acquisition metadata are never rewritten. Duplicate printings are separate physical IDs. No printing/certificate matching, implicit acquisition, copy deletion or guessed metadata.

Graded copies, frozen/converted collections or sources, changed manifests/origins, changed slot set/order, changed configuration/grid, all-inventory/multiple collections, appearance/settings, asset packaging and CSV are **excluded**, rather than silently omitted. An extra unrelated current copy remains untouched. Historical item/slot/root versions are not restored; reviewed current versions fence the request and roots/affected slot/placement versions advance monotonically. Layout is unchanged.

## Provenance and trusted planning

A file contains desired data, **not verified export provenance**. Equal owner/collection/item IDs never establish historical origin or authority. `planRawContentRestore` requires a process-branded complete current owner read, trusted current actor/owner/auth-session or REST/MCP credential/transport, current partner plus partnership ID, and explicit current collection/ordered slot/release selections. Source copies must already exist as raw copies with unchanged identity/acquisition metadata. The returned recursively frozen plan names every current precondition and exact placement change. It never claims a file was exported by this owner.

`prepareAppRawContentRestore` reauthenticates the first-party caller, reads the complete private RLS inventory/grid state and checks live membership. `confirmAppRawContentRestore` re-reads before initial confirmation. Paid/unlimited planning uses the bounded desired-minus-current saved-entry increase, including wanted entries and status markers, instead of an independent 1,024-entry ceiling; SQL independently enforces current allowance. Neither helper is a public route. Backup file inspection remains local and read-only; the separate explicit review/confirmation composition is described below. The old arrangement planner and v1/CSV paths are unchanged.

The shared bridge requires the app's original `X-Binder-Owner` and `X-Binder-Auth-Session`, compares the latter to verified JWT claims and the retained planning scope, and binds actor/source/credential from trusted authentication. REST keys and MCP OAuth require both `collection:write` and `binders:write`, current premium access and the existing budget/revocation checks. Request planning fields are preconditions and cannot select an owner. The SQL service-only gateway independently checks current actor/owner/source/credential and locked partner/partnership evidence.

## Transaction and original-request delivery

095 adds one revoked private `restore_raw_content_v2` helper and narrowly guards exact v1/v2 dispatch in the existing gateway. No historical migration through 094 changes. Existing helper definitions, ownership, ACLs, RLS and billing stay intact. The original ledger digest and namespace are preserved; v2 uses `raw_content_restore_v2`, and gateway fencing checks both namespaces, including terminal v1 rejections. Live membership uses retained `FOR SHARE` locks before common owner locks 6102/4701. The helper locks owner revision, collection/layout/content state and every exact item/placement/slot ref. It rejects converted/frozen state, missing raw copies, changed current refs and mismatched slot order before writing.

One transaction releases reviewed placements, updates the existing slots in place, inserts only exact existing-copy placements, validates current catalog/target/wanted-person constraints and allowance, advances content/owner roots, captures one actor-attributed `backup.restore.raw` event through 076 and stores a permanent version-specific receipt in the existing `developer_idempotency` ledger. Before writes, v2 budgets the complete prospective private before/after graph, including old wants and duplicated manifest roots. Within the mutation rollback scope it flushes the actual existing recorder, compares the generated inverse exactly to that graph and requires the maintained native recovery planner to support it without conflicts. The recorder remains the final atomic guard. No inverse is silently omitted. A later item/slot/placement dependency change, including ABA, invalidates inverse recovery. Recovery adds linked history and advances current roots; it never rewinds versions.

`deliverAppRawContentRestore` forwards the original retained command through `executeAppStorageRequest`. It intentionally does not reconstruct a current plan before SQL's lifetime ledger lookup. Exact accepted **and rejected** replay precedes mutable revision/catalog/slot reconstruction, after current authorization/partner checks. The digest binds the complete original request, owner and gateway context, including actor, source, credential and original operation/batch ID. Changed body/context conflicts. An accepted receipt is historical acceptance, not current state.

Only explicit dedicated SQL predicates produce committed terminal rejection: `inventory_revision_conflict`, `raw_restore_collection_conflict`, `raw_restore_content_conflict`. The private subtransaction rolls back before recording the original-ID-bound rejection in the permanent ledger. Ordinary SQL conflicts, duplicate IDs, allowance errors, cancellation, malformed output, transport loss and **failed COMMIT** remain unknown. A provisional SELECT result inside a transaction is not a committed receipt. Failed COMMIT rolls back both effects and ledger.

## Precise consumer contract

1. Use trusted current complete private read and original authenticated scope, resolve current collection/slot IDs explicitly, show all content changes and exact from/to/release choices, then confirm the frozen plan.
2. Durably retain the **entire original command and authenticated recipient scope** before first delivery. Do not rebuild it from the file, current data, public/redacted DTOs, new IDs or a later session. The durable first-party consumer below supplies browser retention.
3. Unknown/cancel/503/409 or failed COMMIT preserves the original intent. Retry that command under its original actor/owner/session or credential/transport; a changed session/scope blocks delivery, never retargets it. Current revocation/unlink/billing can block historical replay.
4. Accept only this family's strict accepted receipt or dedicated rejection from the trusted original-ID-bound delivery. A JSON-shaped error or matching operation ID alone is not noncommit proof. REST uses 409 `storage_restore_rejected`; MCP uses `isError` and the same typed `error.rejection`. Accepted output schemas exclude errors; discovery declares `holofolder.com/errorSchemas` separately.
5. After acceptance or terminal rejection, obtain a **new complete current owner/session read started after the response**, then explicitly reconcile/discard or review a new plan with a new operation ID. Neither receipt nor proof ACKs local edits or authorizes automatic retry with refreshed revisions.

The original 094 backend slice did not edit BrowserSession/offline queue/sender/rejection consumption. The first-party consumer below adds original-intent durability, post-response complete-read fences and explicit ACK/discard behavior.
