# Staged slot and inventory offline intent

Related: #363, parent #357. This is a device-private preparation boundary, not an enabled app feature or supported REST/MCP API. The current legacy app, bootstrap, offline shell and queue are unchanged. No component currently imports `useSlotOfflineQueue`. Slot/inventory routes remain unconditional private/no-store 503; executors remain runtime-denied. No real conversion, account operation, inventory move or hosted write is part of this change.

## Contracts and persistence

`lib/domain/slot-commands.ts` and `inventory-commands.ts` contain the existing strict command parsers/types extracted from server operations. Server exports and executor signatures remain compatible. Browser validation uses TextEncoder for UTF-8 size, with no Node Buffer/server/admin imports. Requests retain independent inventory, collection, layout, slot, selected item and placement predicates. Existing pure domain and plan helpers drive the optimistic projection; no duplicate inventory schema, SQL implementation or server authorization is introduced.

`lib/collection/slot-offline-queue.ts` is the **only staged queue authority**. It uses one versioned `slot-intent:v1:` record per device, anonymous workspace, authenticated account and resolved owner, inside the existing `binderdex-offline` / `records` store. Original database name/version, localStorage keys, legacy collection mirror and SW protocols are unchanged. No new object store, cache, localStorage queue, dual writer or schema-clearing migration is added. Collection IDs and stable slot/item IDs remain in commands, including cross-collection operations under the same owner. Two same-printing copies remain separate items.

The record contains the last complete owner snapshot, optimistic snapshot, ordered pending intents, acknowledgment/supersession/cancellation receipts and optional opaque legacy archives. A synchronous IndexedDB read/modify/write transaction updates them together and serializes tabs. Enqueue resolves only after transaction commit. Storage/clone/abort errors reject without acknowledging an edit or replacing older intent. No pending intent is evicted to make room. Callers must surface the error and keep an unsuccessful edit recoverable. This deliberately does not use the existing delayed localStorage mirror for staged saves.

Each pending operation retains its real operation ID, exact request, original source/client/batch/clientOccurredAt, complete base and retry/conflict metadata. Intent rejects actor/affectedEntities or arbitrary audit fields. The pure preview uses an ephemeral Unknown actor only to call existing plans; it is never serialized as authenticated evidence. A future authenticated adapter must establish the current actor and validate original provenance under #394. No local intent is committed audit history.

New/future/malformed record versions fail closed, retaining the original bytes. Unknown legacy queue shapes remain opaque raw bytes rather than being filtered. `preserveLegacy` is an explicit additive archive adapter: it never removes or rewrites the legacy queue, nor converts archived ops into uploadable commands. Known operation IDs are mapped with `legacySlotId`, identical to migration 073. Stable workspace IDs survive unchanged, including malformed entries and multiple distinct operations for the same printing/species. Do not archive another account's legacy record into the current scope. The final conversion adapter must explicitly establish its source owner/workspace before calling this boundary and atomically retire old write authority; this PR does not create two replayable copies of legacy work.

Guest records require both account and owner to be null; their snapshot owner is their workspace ID. Replay refuses guests. Signing in, account switching or resolving a partner owner selects a different record and never retargets guest copies. Recipient confirmation/import acceptance remains explicit in #365/#379; it cannot infer identity from a printing or automatically upload a guest archive. `useSlotOfflineQueue(scope, sessionId)` hides the previous session's state synchronously and invalidates in-flight replies when its authenticated session ends. The integration must change `sessionId` on sign-out, account switch and unlink/relink, even when the resolved owner later becomes the same. Cross-tab notifications contain only a change signal, never private snapshots or IDs.

## Replay and reconciliation

Only the head operation is sent, under a persisted 60-second lease. Competing tabs cannot claim it concurrently. After a crash, an expired lease retries the **same exact request and operation ID**. Unknown outcomes, network errors, invalid/mismatched replies, 5xx and the staged 503 retain durable intent. Retry delay is bounded exponential backoff (1 second to 5 minutes), at most five automatic attempts. `resume` is an explicit retry of the original ID, including after billing/authorization is restored. A live lease or unresolved conflict prevents arbitrary retry/reset.

The injected replay adapter is an **internal capability**, not a fetch implementation. A 200 acknowledgment must carry the matching operation ID and a complete, freshly validated owner snapshot. `readCompleteInventorySnapshot` brands only a successful all-stream read; a plain, partial or persisted-looking object cannot acknowledge a save. A future supported adapter must read current state after ledger replay, because the retained ledger result can predate newer partner edits. Receipts prevent the same local operation from being enqueued again. A late result from an obsolete lease/session cannot settle newer work. Appending another edit does not replace the head or coalesce by species/printing.

402 pauses billing, and 400/401/403/404 block the operation visibly. 409 retains the exact original request plus current scoped state. Only recognized precondition/selection conflict codes establish the known-rejection flag; idempotency_conflict and unclassified 409 never authorize cancellation or a new ID. No hard error silently rolls back or removes intent. A 409 without complete current state cannot be rebased. A newly read base that cannot project dependent work records a visible conflict; it does not rewrite the request or silently manufacture a new ID.

Explicit `rebase` is limited to one known-rejected operation, with no dependent queue, comprising unchanged selected slots for content updates or unchanged items/placements for grade metadata. Unrelated remote edits survive. It checks layout and relevant slot/item/placement state independently, adopts current outer revisions and requires a new operation ID. The rejected request/provenance remains in a superseded receipt. An edit touching a changed slot, placement or copy cannot use this path.

Reorder, structural insert/remove, assignments, selected wants, deletes and moves/swaps require an explicit reviewed intent when conflicting. `reconcile` can retain remote state or supply a newly checked full replacement command against the complete conflict snapshot, with a new ID; the original remains recorded. These decisions are disabled for unknown outcomes, unavailable state or dependent queues. There is no automatic last-write placement theft, missing-copy cloning, stale selected-grade conversion to a generic catalog choice, remote-deleted-slot resurrection or implied acquisition. Safe undo is another explicit inverse command with current stable IDs and predicates, not a rollback that overwrites a newer partner move. Generic catalog selection keeps the accepted reuse/create policy; an explicit existing-copy selection never falls back to creating a copy.

## Complete reads

`readAllSlotPages` consumes the actual 074 `SlotPage` contract. It carries inventory/collection/layout revisions on every continuation, checks increasing positions and unique IDs, rejects changing revisions/cursors/partial pages and collects beyond 1,000 rows before publishing anything. The caller restarts the entire read with bounded retries after a revision conflict; no accumulated partial page is authoritative.

There is no enabled owner-wide inventory read API yet. `readCompleteInventorySnapshot` provides an internal adapter for four complete stable owner-revision streams (items, placements, collections, binders). Its callbacks must bind authenticated scope, stable keysets and authoritative totals; totals are an internal completeness assertion, not invented fields on the current HTTP routes. The binder reader must call `readAllSlotPages` and map every returned stored slot under matching inventory/collection/layout revisions. Repeated identities, changing totals, missing rows and failed streams reject the entire read. Domain normalization then verifies all placements/slots/items form a complete owner-scoped bijection. #376 owns supported reads, status mapping, registry/OpenAPI/MCP and auth/provenance binding.

The first-party authenticated table binding is now prepared in `lib/server/inventory-read.ts`. See [complete-read mapping, errors and scope boundaries](inventory-complete-read.md). It validates current session/membership/billing and all paginated streams before branding, with whole-attempt retry and a shared deadline. It remains internal and unwired: queue ACKs must call it after ledger replay, and legacy/mixed owners explicitly remain unavailable. Developer REST/MCP grants and rollout are separate gates.

## Proof and remaining gates

Run focused units and the real-browser storage proof:

```sh
bun test tests/binder-slots-offline.test.ts tests/slot-optimistic.test.ts tests/slot-snapshot.test.ts tests/offline-store.test.ts tests/collection-offline-queue.test.ts tests/collection-sync.test.ts tests/binder-slots.test.ts tests/binder-slot-operations.test.ts tests/binder-slot-targets.test.ts tests/inventory-model.test.ts tests/inventory-operations.test.ts
node scripts/verify-slot-offline-storage.mjs
bun run typecheck
bun run lint
bun run build
```

The browser proof bundles the actual library with Bun and runs synthetic Chromium contexts at 375×667, 390×844 and 430×932, with browser/emulated standalone display mode. It verifies real IDB commit/abort, simultaneous tab transactions, offline reload, durable 503 intent and unchanged legacy records. It starts no server and makes no external request. This is storage proof, not an installed-PWA/UI/real-SW rollout test. No UI/overlay or SW change is included; the full e2e suite is not run.

Still gated: #361/#362/#383 runtime compatibility, #394 transactional audit/provenance, #396 recovery, #376 supported API/read adapters, #365 guest recipient acceptance and #379 conversion/bootstrap/rollout and full app offline UI integration. The accepted large-collection deletion/256-work limitation, mixed-legacy default replacement and auxiliary recovery gaps remain with #383; this queue does not replace them with manual deletion UX. Receipts and per-operation complete base snapshots intentionally favor retention; measuring/compacting acknowledged state without losing IDs/provenance and testing realistic device storage pressure remain pre-exposure work. Unknown schema data or quota failure never authorizes clearing intent. No enabled customer feature, generated public endpoint or release announcement is claimed. #363 remains open through those integration checks.

Explicit resume may reclaim an expired send lease, including an interrupted fifth attempt, while retaining the original operation ID. Live leases remain protected. Optimistic swaps increment each affected slot version once, matching the SQL executor so dependent queued commands retain valid preconditions. Repeated slot touches within a batch and selected-want printing/finish mismatches are rejected locally as well as by SQL.
