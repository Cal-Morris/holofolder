# Native developer registry integration, staged (#376)

This slice registers seven native command/creation/recovery operations in the existing `DEVELOPER_OPERATIONS` allowlist. Both real REST and MCP handlers validate the same strict structural Zod schemas; canonical domain parsers retain the authoritative cross-field and byte constraints. `executeNativeDeveloperOperation` revalidates schemas and permissions even for trusted direct dispatcher callers, then invokes the existing `executeDeveloperStorageOperation` and `storage_execute_v1` bridge after admission. There is no competing store, identity, command executor or audit/receipt implementation.

## Admission and current behavior

`requireNativeDeveloperAdmission` always throws `503 native_operations_staged`. It accepts no argument and reads no environment or credential override. Valid permitted commands never reach the executor in production. Discovery/OpenAPI/Markdown/LLM exports explicitly call the operations staged; response schemas describe future post-admission receipts only. Existing public first-party inventory/slot routes stay unconditional 503, and the first-party host, BrowserCollectionSession, queue sender, bootstrap and service worker are untouched.

All command/creation operations require `collection:write` and `binders:write`; native recovery also requires `collection:read`. Existing key/OAuth authentication resolves current owner/partner scope, paid developer entitlement, revocation and budgets. Native preview consumes read budget; apply/commands consume write budget. The SQL bridge rechecks actual authority, billing and caps, binds actor/source/credential and stable operation/batch IDs, and projects receipts through the maintained sanitizer. Native operation IDs are in the body, not an additional legacy idempotency header. No SQL or grant change is made.

The shared transports now accept per-operation body bounds, retaining existing limits for legacy operations. Native intent limits remain canonical: 256 KiB ordinary slot/inventory, 8 MiB sole collection deletion, 2 MiB copied creation, 1 MiB recovery. MCP JSON-RPC framing gets an additional bounded 64 KiB; tool arguments still have their exact operation budget. Malformed schema arguments may be rejected by the MCP SDK before its callback; these existing SDK errors are not fabricated as executor errors.

Native requests map only to the already implemented slots, inventory, collection.create and recovery.preview/apply v1/v2 bridge operations. The existing `preview_collection_recovery` and `apply_collection_recovery` registry entries and 087 legacy facade are unchanged. There is no native-to-legacy fallback. Unsupported native events remain explicit conflicts/unsupported plans. Native creation receipts retain conservative `recoverySupported:false`.

## Exact complete-read incompatibility and remaining scope

`lib/server/inventory-read.ts` explicitly requires its request's cookie/RLS client. `readOwnerInventoryState.scope()` verifies authenticated first-party claims with no client_id, a session_id, a matching getUser result, current RLS partnership and billing policy, and repeats those fences. Its private planning state includes certificates/assets/immutable source evidence and explicitly forbids developer serialization. REST keys and the app's OAuth MCP grants are separately verified credentials, not Supabase cookie sessions. Passing the admin client, a fabricated getClaims/getUser adapter, a caller-supplied owner or an unrelated browser cookie would bypass this contract.

The follow-up [trusted developer read slice](native-developer-read.md) extracts the shared query/normalization/fence core behind separate cookie and verified developer authority adapters. Five strict read operations now declare the authenticated redacted projection and signed scope/filter/revision-bound pagination, with the same fixed admission denial. No admin client enters the cookie reader and no private complete snapshot crosses REST/MCP. The tests/proof and privacy policy for those reads are documented separately; this command slice's original complete-read prerequisite is now implemented locally, awaiting independent review and parent shipping.

Preset list/preview, native compatibility/consumers, first/default/mixed-owner bootstrap, original-recipient durable replay/fresh-read ACK, offline relaunch, hosted timeout/cancellation/load, native recovery acceptance and literal #379 admission remain open with their owning lanes. No migration, hosted access, conversion, public-share widening, scanner edit, merge/watch or publication occurs here.

## Private-preserving command mode (#376/#383)

Both command operations now accept optional `privateFields:"preserve"|"replace"`. Omission remains fully compatible with the original replacement contract. Preserve mode requires `expectedOwnerUserId`, checked against authenticated current owner scope before any execution (`409 storage_owner_changed`), including when no receipt exists. This is a recipient precondition, never authority or a scope selector. Replacement mode can opt into the same fence. Preserve mode is an allowlist assertion: slot create/reorder/target-only update; inventory add/explicit removeOwned/unassign and assign/move with `fulfillWant:null`. It rejects every grading edit, wanted-array replacement, selected-want fulfilment and slot/collection deletion. Explicit whole grading/wants clearing stays available only through the unchanged replacement contract. This distinction is included in OpenAPI, current help and derived Markdown/agent exports; no new operation or navigation group is introduced.

The dispatcher revalidates the assertion and removes only the assertion and checked recipient precondition before invoking the existing bridge. No privileged read or server reconstruction occurs. Canonical request bytes, original owner/actor/credential/source/operation-ID binding and preconditions therefore retain the existing lifetime ledger behavior, including replay after later changes. The assertion fields are not part of ledger identity (owner is already bound by the SQL digest): switching between omission/replace/preserve for the same permitted canonical intent produces the same ledger request. Preserve cannot make an unsafe intent admissible. It does not grant a read DTO complete-snapshot or queue-ACK authority.

### Concrete SQL prerequisite, no SQL in this lane

`075_inventory_commands.sql` hashes owner, full request and trusted intent, then looks up the actor/operation receipt **before** checking current revisions. Its `edit` branch replaces the full grading record; `fulfillWant.expected` compares the full stored JSON, including fields the developer read intentionally redacts. `074_atomic_slot_commands.sql` similarly replaces a supplied wanted list. The `082` bridge accepts only these existing canonical contracts. Consequently an HTTP-side private read/merge would either erase hidden data or change the replay digest after a successful request/later edit. No read fallback, in-memory cache, additional ledger or parallel migration solves that guarantee.

The SQL-owning lane must add an explicit intent-based patch/selected-want contract within the existing authorized transaction and lifetime ledger. Digest and replay the original caller intent before reconstructing any current record; lock/check the original owner, item, destination, collection/layout and want preconditions; distinguish omitted fields from authorized explicit clearing; preserve unrelated private wants, grading/assets and immutable source evidence. Return only sanitized receipts. Grading/fulfilment parity remains blocked until that contract and its real transactional concurrency/replay proof exist. This lane does not allocate or edit 089, change the first-party queue or enable admission.

Lost replies after synthetic ledger commit, later operations, unchanged replay, changed-body/recipient conflicts, unsupported redacted replacement and existing paid/role/scope fences are covered. Intercepted PostgREST ledger behavior proves forwarding, not PostgreSQL atomicity/concurrency or hosted authority. No SQL test or hosted access is claimed.
