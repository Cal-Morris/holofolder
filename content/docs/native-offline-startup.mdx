---
title: Saved collections offline
description: What saved startup can show and when a connection is required.
---

Visit the app online first so this device can save its app files and collection data. Saved native collections can then reopen in Binder, List, Slabs and Inventory, labelled **Cached only**. Pending changes stay on this device until synchronization succeeds.

## Account and saved state

Offline startup needs the same unexpired device account session and saved collection-owner scope. Shared cached collections also need the account/owner-matched saved partner access allowance. This is permission to display saved copies, not proof of current membership or confirmation that pending changes reached the server.

Layout editing, new storage and remote commands are unavailable in cached startup. On reconnect the cached view closes and current account and collection access are checked before fresh data or commands can be used. Partner/account changes close the previous private view and its dialogs. Pending edits stay in their original scoped device record.

If a complete refresh fails, the app keeps saved copies and pending changes, shows why it cannot refresh and disables new edits. Use **Refresh storage** after reconnecting. Missing, corrupt or expired account evidence or saved metadata requires a connection; the app does not manufacture an empty collection or delete pending edits. A first-ever offline visit cannot open an app whose files were never cached.

## First collection

On an initialized new account, choose **New storage**, preview the arrangement and confirm it. The first storage becomes your default after the server confirms the creation and the app reads current storage. A failed or unknown reply keeps the original creation pending; do not create a duplicate to replace it.

If the app says your native collection is not ready, an administrator must initialize the new account or finish converting its existing collection. The browser never converts existing legacy data automatically.

These startup and presentation preferences live on this device and add no REST or MCP operation. Existing native API credentials and server admission are separate from browser account checks. Physical-device and production verification remain release requirements.
