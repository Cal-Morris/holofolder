## Activity in the app

Open the binder switcher and choose **Activity**, or open **Activity** from a card’s details to see just that Pokémon. Entries are grouped by day and say what happened, such as **Removed Bulbasaur from My binder**, with the printing, person and local time.

Simple additions and removals are compact receipts. Tap an available card title to open that card in the current binder. Choose **View changes** for meaningful before/after values such as a printing swap; bulk changes expand a few at a time. Ordinary receipts avoid raw event data. Exact-operation history navigation identifies the original operation and selected event explicitly. A previous member is labelled **Previous member**; an unattributed entry stays **Unknown**. These labels do not invent historical profile names.

**Filters** searches the complete recorded history, including deleted cards. Choose a collection, person, action or inclusive UTC date range. **Older page** and **Newer page** follow server cursors, including histories longer than 1,000 events. Displayed times use your device’s timezone.

## Undo a mistake

Choose **Undo**, review what will be restored or removed, then choose **Undo this change**. Complete recorded card and want-list row edits are supported, including removing a card, changing its printing/status and editing wanted cards. A supported bulk event is undone together.

Undo restores the original row identity and recorded card details. It checks current access, collection format, current limits and later changes to the same Pokémon. It refuses a newer edit even if the visible card was subsequently changed back. Unrelated later changes survive. There is no force overwrite.

Undo adds a new history entry and keeps the original. The original receipt shows **Undone** after verification, and when its linked undo is present on the loaded history page. The short-lived Undo for an acknowledged card edit uses the same checked recovery command. Unsynced edits keep their existing device undo path.

Collection creation/deletion, settings, sharing, native inventory/slot operations, collection-format changes and older entries without complete evidence cannot be undone through this release. Undo is offered for recorded card and want-list edits; its preview explains conflicts with newer work. Internal native recovery preparation remains separately gated.

## Offline and connection failures

Previously opened activity pages remain available on this device, with their last-update time. They are saved pages, not a complete offline history. Reconnect to load another page or undo a change. Pending local edits must sync before Activity Undo is available.

If a connection fails while Undo is being applied, choose **Retry Undo**. The app retains the exact request before sending it and checks the same operation again, including after closing Activity or reloading. A retry cannot apply it twice. It refreshes the collection before showing **Undone**. If the write succeeded but the refresh failed, it says the undo was saved and offers verification again.

## REST and MCP

Developer access requires current entitlement, credential grants and owner/linked-partner access. The app uses its signed-in session. Responses are private and use `no-store`. Public share links have no private Activity.

`list_collection_audit` (`GET /collection/audit`) and `get_collection_audit` (`GET /collection/audit/{id}`) require `collection:read`. Event IDs are strings. Lists return `data` and `nextCursor`, with up to 100 entries. Keep the same filters when following a cursor. Filters include `collectionId`, `pokemonId`, `cardId`, `itemId`, `slotId`, `actorId`, `action`, `since`, `until` and `recoveryOfEventId`. The last filter finds undo events linked to an original. An undo entry also includes `recovery_of_event_id`.

`preview_collection_recovery` (`POST /collection/recovery/preview`) and `apply_collection_recovery` (`POST /collection/recovery/apply`) require `collection:read`, `collection:write` and `binders:write`. They share the app’s supported scope and checks. Preview changes no collection data. Its response includes `supported`, `unsupported`, `conflicts`, safe `changes`, `planVersion` and `planToken`. A conflict or unsupported event has no usable token.

Synthetic preview example:

```bash
curl 'https://app.holofolder.com/app/api/v1/collection/recovery/preview' \
  -H 'Authorization: Bearer <key>' \
  -H 'Content-Type: application/json' \
  -d '{"eventId":"123","restoreUnassignedItemIds":[]}'
```

After reviewing the preview, apply that exact token with explicit confirmation and a new operation ID. Preserve this entire request for retries:

```json
{
  "eventId": "123",
  "restoreUnassignedItemIds": [],
  "planVersion": 1,
  "planToken": "<64-character token from preview>",
  "operationId": "<unique retry-stable operation ID>",
  "confirmed": true
}
```

Apply returns `{ "eventId": "<new undo entry>", "recoveredEventId": "123" }`. After an unknown outcome, retry the same request, account and owner. Never generate another operation ID to retry. A later edit invalidates the reviewed token (`409`); current permission or allowance checks can also reject recovery. Rejected recovery leaves the collection and history unchanged. No acquisition notification or sharing token is replayed.

The history recorder requires migration 076; linked recovery reads require 077 and the supported recovery command requires 087. Missing schema returns a temporary-unavailability response. Private certificates, label assets, uploaded artwork references and share tokens are excluded from public history and recovery responses.

## Native storage recovery is still staged

The native storage host has a prepared Activity review flow, but native recovery is **not enabled**. Its first-party route and registered native REST/MCP operations return `503 native_operations_staged`. The ordinary card and wanted-row Undo described above remains the supported capability.

The prepared native flow reviews safe changes and explicit conflict reasons online. It requires specific review for restoring a removed copy as Unassigned or nominating a replacement default collection. Private label artwork that cannot be verified remains unavailable. Confirmed native requests would be retained in the existing device queue, with exact retry after unknown results and a new complete current-state read before synchronization. There is no offline optimistic restoration, automatic new request, or inferred successful Undo. Backend/public transport and rollout acceptance remain tracked in #396/#379; this preparation is not a release announcement.


### Prepared native recovery rejection

Native recovery remains staged and returns `503 native_operations_staged` before execution. The prepared v1/v2 apply contract declares REST `409 storage_recovery_rejected`, or MCP `isError:true`, only for a committed strict `error.rejection` containing `outcome:"rejected"`, the original `operationId`, known `code` and `inventoryRevision`. Codes are `recovery_plan_conflict` and `recovery_dependency_conflict`. Arbitrary 409/SQL errors, missing receipts, cancellation and billing/access errors are not noncommit proof. Exact accepted/rejected replay requires current authority and precedes mutable plan reconstruction.

In the staged app, durable proof permits a separately fresh complete current owner/session read and explicit **Discard noncommitted recovery**. Discard preserves original request/proof with a distinct discarded state, never accepted/synchronized. **Review new recovery** then needs a new preview and explicit confirmation with a new operation ID. Unknown and accepted requests never gain discard/rebase. The existing legacy Undo contract is unchanged; no private inverse, evidence, certificates or assets are exposed. This preparation is not an enabled capability or release announcement.

### Find an exact operation

REST `GET /app/api/v1/collection/audit?operationId=synthetic-original-operation` and MCP `list_collection_audit` with `{"operationId":"synthetic-original-operation"}` find the exact original operation within your currently authorized history. The example ID is synthetic. Keep the same filters when following `nextCursor`, then use `get_collection_audit` with the selected event ID to inspect it. An empty result does not prove that a command failed. Multiple events require choosing an exact event; never use the newest event as a guessed inverse. Operation IDs are bounded opaque strings, up to 200 characters without surrounding whitespace or line breaks. Private recovery evidence remains server-only.

The staged native browser prepares **Find acknowledged change** only after a saved command has passed its separate fresh complete sync verification. It then requires a new history lookup and an exact-entry read before any supported **Review recovery** preview. Cached/offline history cannot authorize this handoff. Native slot/inventory/recovery execution remains disabled in production; this preparation does not announce native Undo as available. Existing legacy card and want-list Undo above is unchanged.
