## Availability

**Native developer operations are staged and unavailable.** Valid authenticated requests return `503 native_operations_staged`. Listing a schema or MCP tool does not enable it. There is no credential, environment option or request flag that bypasses this gate. Existing legacy collection and Activity Undo APIs keep their current behavior.

The staged command contracts reuse the app's trusted native executor. Five [staged developer reads](/docs/native-reads) declare redacted pages/details with current preconditions. They remain unavailable and always declare `completeSnapshot:false`; they never provide a private planner snapshot or queue acknowledgement. Public binder links never grant access to private owner inventory, certificates, label assets or location.

[Copied preset discovery/preview](/docs/preset-previews) adds separate staged read-only operations requiring `catalog:read` and `binders:read`. They return public preset metadata or detached copied goals, allocate no creation identities and expose no private planning state. Set/master-set durable scope remains unsupported.

## Credentials and permissions

REST uses a personal API key at `https://app.holofolder.com/app/api/v1`. MCP uses its separately approved OAuth grant at `https://app.holofolder.com/app/mcp`.

Slot commands, inventory commands and copied creation require both `collection:write` and `binders:write`. Native recovery additionally requires `collection:read`. The existing current owner/partner membership, paid developer entitlement, revocation and read/write budgets apply before staging denial. Trial access alone does not grant developer access. No new grant or database permission is introduced.

## Commands after admission

These are contract names, **not currently enabled workflows**:

| REST POST path, relative to the API root | MCP tool | Contract |
| --- | --- | --- |
| `/storage/slots/commands` | `execute_slot_commands` | Insert, update, clear, remove and reorder stable slots atomically |
| `/storage/inventory/commands` | `execute_inventory_commands` | Add, edit, remove ownership, assign, move, unassign and delete storage atomically |
| `/storage/collections` | `create_storage_collection` | Create native storage from an ordered copied manifest |
| `/storage/recovery/preview` | `preview_storage_recovery` | Review supported native event recovery |
| `/storage/recovery/apply` | `apply_storage_recovery` | Apply the exact confirmed version-1 native plan |
| `/storage/recovery/v2/preview` | `preview_storage_recovery_v2` | Review default-creation recovery with an explicit replacement |
| `/storage/recovery/v2/apply` | `apply_storage_recovery_v2` | Apply the exact confirmed version-2 native plan |

Targets describe goals. A null target is a free slot, not a wanted card. Wants are explicit entries. Each assigned slot needs its own physical copy; moving preserves copy identity and empties its previous slot. Clear/remove release owned copies to Unassigned. Only `removeOwned` removes ownership. Collection deletion must supply its exact complete slot preconditions; it is not an ownership deletion.

Every command retains its `operationId`, stable copy/slot/collection IDs and exact revisions across retries. Slot commands include inventory, collection and layout revisions, plus the selected slot/item/placement versions. A copied manifest has ordered targets and immutable source/entry identities. Creation never silently invokes legacy creation or rewrites a preset later. Current completion uses current targets, not the original manifest count.

This synthetic slot insertion illustrates the schema only. It currently returns staging denial with permitted credentials:

```bash
curl https://app.holofolder.com/app/api/v1/storage/slots/commands \
  -H "Authorization: Bearer $HOLO_FOLDER_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"collectionId":"00830000-0000-4000-8000-000000000011","operationId":"synthetic-slot-insert-1","inventoryRevision":1,"collectionVersion":0,"layoutRevision":0,"commands":[{"kind":"create","ids":["synthetic-slot-1"],"beforeSlotId":null}]}'
```

MCP calls `execute_slot_commands` with that same JSON object as arguments. Native intents use body `operationId`, not the legacy creation `Idempotency-Key` convention. Reuse the same credential and transport for a retry; actor, credential, source and request-body changes can conflict with the permanent native ledger. A historical receipt is not a fresh read or proof of current placement. Unknown outcomes require exact replay followed by a fresh authoritative complete read before acknowledging the edit.

## Preserve private fields

For `execute_slot_commands` and `execute_inventory_commands`, set the optional top-level `privateFields` to `"preserve"` and include `expectedOwnerUserId` for the original recipient. Both transports and the dispatcher check this assertion. New public patch intents are resolved only inside the locked transaction, after original-intent replay lookup (migration 090). `expectedOwnerUserId` must match current authenticated owner scope; it never selects an owner or grants access. A changed scope returns `409 storage_owner_changed` before execution, even when an unknown first attempt never committed. The original full-replacement contract may also opt into this recipient fence. Valid permitted calls still return staging denial.

| Preserve mode accepts | Preserved data |
| --- | --- |
| Slot `create`, reorder `move`, and `update` with only `target` | Existing wanted entries, including hidden attribution and images, are untouched |
| Inventory `assign` or `move` with `fulfillWant:null`, and `unassign` | Existing grading, certificates, label assets, provenance and wants are untouched |
| Inventory `patchGrading` on an already graded card copy | Omitted public fields, certificate, private label assets and immutable provenance survive |
| Inventory `assign` or `move` with `fulfillWant:{index,expectedPublic}` | Only the exact selected entry is consumed; hidden fields and all other wants remain private and unchanged |
| Inventory `add` | Creates only the supplied new copy, never reconstructs an existing copy |
| Inventory `removeOwned` | Explicitly deletes that copy; unrelated copy metadata and wants remain untouched |

Preserve mode rejects full grading `edit`, wanted-array replacement, full-private `fulfillWant.expected`, slot clear/removal and collection deletion as invalid input. Use the full-replacement contract only when intentionally replacing or clearing those fields. Omitting `privateFields` retains the existing contract; `"replace"` explicitly selects the same behavior. A grading `edit` replaces the **entire** grading object, including certificate and label assets; `grading:null` explicitly removes it. A slot `update` with `wantedCards` replaces the **entire** list; `wantedCards:[]` explicitly clears it. Neither is a patch. Existing full selected-want requests retain their exact index and full `expected` equality check. Never fill omitted private values with null or rebuild either replacement from the redacted read model.

Synthetic target-only request for REST `/storage/slots/commands` or MCP `execute_slot_commands`:

```json
{"privateFields":"preserve","expectedOwnerUserId":"00820000-0000-4000-8000-000000000001","collectionId":"00830000-0000-4000-8000-000000000011","operationId":"synthetic-private-target-1","inventoryRevision":7,"collectionVersion":2,"layoutRevision":1,"commands":[{"kind":"update","slot":{"id":"synthetic-slot","version":3,"inventoryItemId":null,"itemVersion":null,"placementVersion":null},"target":null}]}
```

Keep this exact request, credential, transport and original recipient for unknown-outcome retries. The assertion and recipient precondition are stripped before the existing executor receives the unchanged canonical intent; no current hidden fields are added to its permanent ledger digest. Only after an exact replay miss does SQL lock/check the current entities and resolve a public patch or selected want. A receipt can describe an earlier successful operation after later edits and must never be treated as current state. Stale/conflicting requests remain conflicts; do not refresh revisions, change recipient or issue a new ID to escape an unknown outcome. Redacted pages/details remain `completeSnapshot:false` and cannot ACK a pending queue.

### Public grading patch and selected want

`patchGrading` accepts `item` with its exact current item/placement/slot versions and a nonempty `patch`. Supported fields are `provider`, `grade`, `scale`, `designation`, `subgrades`, `holder` and `labelVariant`. Omission retains the stored value. Explicit `null` clears nullable text; `subgrades:[]` clears subgrades. Provider must remain a complete valid provider object. Certificates, asset IDs, acquisition time and immutable provenance cannot be patched. The copy must already have a grading record; this does not create grading on a raw copy or clear the whole record. Use intentional full replacement for those cases.

For `assign` or `move`, `fulfillWant:{index,expectedPublic}` consumes exactly one entry at an integer index from 0 to 99. `expectedPublic` must equal the selected entry's complete declared public projection: `card_id`, `card_name`, `added_at` and any present `card_language`, `card_finish`, `card_set`, `rarity`, `local_id`, `illustrator`, `set_total`. It excludes `wanted_by` and `card_image`. Retain the exact destination slot ID/version, item and placement preconditions, collection/content/layout and owner inventory revisions. Duplicate wants never trigger a search for another matching entry. Missing/mismatched public fields or any stale revision reject the whole batch.

Synthetic inventory request, usable as the same REST `/storage/inventory/commands` or MCP `execute_inventory_commands` arguments after admission:

```json
{"privateFields":"preserve","expectedOwnerUserId":"00900000-0000-4000-8000-000000000001","operationId":"synthetic-grade-patch-1","inventoryRevision":3,"collections":[],"commands":[{"kind":"patchGrading","item":{"itemId":"synthetic-unassigned-copy","itemVersion":2,"placement":null},"patch":{"grade":"10","holder":null}}]}
```

A committed operation with a lost reply replays its original sanitized receipt after later grading, want or placement edits, without overwriting those edits or adding audit events. Body/owner/trusted-source changes conflict; current membership, scope and paid access are checked again before replay. Retain the original operation and IDs across unknown outcomes. The 10-second executor deadline is unchanged and a timeout does not establish noncommit.

These intents require migrations 089 and 090, already applied by the parent with retained restore-verified backups. Native tables remain empty, with zero conversions and no hosted native commands. They remain staged behind the same unconditional `503 native_operations_staged`. Local SQL proof against 088+090 does not prove combined 089 behavior. Existing native recovery records real inverse evidence; private-label-asset events remain unsupported with `private_assets_unverifiable`, and newer changes conflict. No public Undo or offline queue ACK parity is claimed.

## Terminal command rejection contract, staged

For `execute_slot_commands` and `execute_inventory_commands` only, a validated committed terminal ledger result becomes REST `409 storage_command_rejected` or MCP `isError:true`. Both return this same safe structured error (synthetic example):

```json
{"error":{"code":"storage_command_rejected","message":"The original storage command was rejected. Refresh current storage before explicit reconciliation.","requestId":"synthetic-request","rejection":{"outcome":"rejected","operationId":"synthetic-command","code":"slot_revision_conflict","inventoryRevision":12}}}
```

`rejection.operationId` binds the original submitted ID. `code` is one of `slot_revision_conflict`, `inventory_revision_conflict`, `inventory_collection_conflict`, `slot_conflict`, `item_conflict`, `placement_conflict`, `inventory_want_conflict`, `inventory_copy_choice_required`, `inventory_destination_empty` or `inventory_destination_occupied`. `inventoryRevision` is a nonnegative safe integer from that terminal outcome, not current storage. No original payload or private metadata is returned.

After a confirmed rejection, load fresh complete current storage and explicitly review reconciliation. A generic 409, stale revision, SQL error, timeout, lost reply or absent ledger read does not prove noncommit. Keep the original immutable command, ID, source, credential and recipient for unknown-outcome retry. Current auth, membership and paid access are checked before replay data; changing identity cannot borrow a prior receipt.

OpenAPI declares terminal and ordinary 409 errors separately from accepted 200 receipts. MCP tool discovery advertises accepted receipts in `outputSchema` and status-keyed error schemas in `_meta["holofolder.com/errorSchemas"]`. The SDK skips success-schema validation for `isError`; the server validates the terminal error before serialization. Text and structured MCP error fields match. Other native creation/import/recovery operations and all legacy errors keep their existing contracts. The first-party private HTTP version-1 409 envelope is unchanged.

**This is a staged contract, not enabled behavior.** Valid authorized public calls still return the fixed 503 before execution. Local synthetic transport proof does not satisfy #379 hosted acceptance.

## Bounds and errors

Ordinary slot/inventory batches allow at most 100 commands and 256 affected work under the canonical planner, with a 256 KiB intent limit. A sole whole-collection deletion has its own 4,096-slot, two-collection, 8 MiB bound. Copied creation allows 4,096 targets under 2 MiB. Native recovery has a 1 MiB request bound. Oversized requests fail as a whole; no truncated page or split batch is reported as complete.

Current authorization/input errors can precede `native_operations_staged`. After future admission, the existing executor maps stale revisions, identity or changed-body replay to `409 storage_conflict`, current membership denial to `403 storage_access_denied`, caps/developer entitlements to 402, malformed constraints to 400 and unsupported recovery to `409 recovery_unsupported`. Unknown backend failures return sanitized `503 storage_unavailable`. REST errors carry `error.code`, `error.message` and `error.requestId`; MCP execution errors use `isError` and the same structured error. Ordinary conflicts are not terminal rejection proof. MCP schema validation can reject malformed arguments before execution using the SDK's validation error.

Native recovery never falls back to the legacy Activity recovery facade. Unsupported or incomplete evidence has no usable plan; newer/ABA changes, dependencies and authority transitions remain conflicts. Version 2 requires one explicit same-owner replacement with its exact current revisions. Copied creation receipts conservatively retain `recoverySupported:false`; use a fresh supported preview, not that receipt, to decide recovery eligibility.

## Remaining gates

Independent review and production acceptance of the staged developer read projection/pagination, preset discovery/preview parity, original-recipient replay and fresh-read acknowledgement, native offline relaunch, compatibility/consumer integration, recovery/load proof and #379 rollout acceptance remain open. No hosted conversion, public share expansion or enabled native workflow is claimed. The OpenAPI receipt schemas describe the staged executor contract; they are not evidence of a current 200 response.

## Staged read projection

[Native developer reads](/docs/native-reads) now declare copy, storage and stable slot reads with current preconditions and revision-bound pagination. They share the fixed admission denial. A returned page cannot serve as a complete planning snapshot or a fresh-read queue acknowledgement.

## JSON v2 arrangement import, staged

`import_storage_arrangement` (`POST /app/api/v1/storage/imports/arrangement`) is registered with both write scopes and fixed `503 native_operations_staged` admission. It does not enable importing in Settings or replace the existing v1/Dex importer.

The prepared backend imports one complete ordered arrangement into existing native storage with the same copied preset manifest. The destination must be empty or have only reviewed empty targets/spacers. Preview lists the replaced empty slots, every added physical copy and every explicit move of a trusted existing copy. Matching printings and certificates never merge ownership. Wants, spacers and recorded grading stay separate; private label assets and appearance/settings imports are unsupported.

Keep the exact immutable operation and generated IDs after a timeout or lost response. Reconfirming a new plan can mean additional physical copies. A historical receipt needs a fresh complete read before showing the import as synchronized. Changed same-owner restore, multi-collection owner restore, CSV fill/append execution, asset packaging and offline import delivery remain unavailable. Current legacy Activity Undo does not undo native imports. The private native recovery planner can recover untouched generated events, including previous explicit placements and empty target layout; later edits or ABA conflict.


## Atomic slot insertion and copy assignment, staged (091)

`execute_inventory_commands` and `POST /app/api/v1/storage/inventory/commands` accept `insertAssign` through the same strict shared registry. Production still returns fixed `503 native_operations_staged`. Migration 091 must follow 090 before this intent can execute; the parent owns hosted application and release.

Each command supplies `collectionId`, a stable **new** `slotId`, `before` as an exact existing slot precondition or explicit `null` to append, `target` as a declared target or explicit `null` for free, and `selection`. It shifts the full saved arrangement, preserving every following target, wants, item and spacer identity. It never replaces a pocket or searches for another destination.

`selection:null` adds only a placeholder, with no ownership. `selection:{kind:"existing",inventoryItemId,itemVersion}` reuses exactly that Unassigned copy once, preserving grading, certificate, acquisition and immutable provenance. Assigned copies cannot be selected. `selection:{kind:"new",itemId,identity,grading,acquiredAt}` explicitly acquires one new copy with stable identity and declared metadata; unknown grading/acquisition are `null`. The caller must review eligible Raw/recorded-copy choices, never infer grading or acquire a duplicate merely because a transport reply was lost. This explicit new-copy form does not broaden the scanner's graded-only Raw policy.

Synthetic example, **not an enabled endpoint**:

```json
{"privateFields":"preserve","expectedOwnerUserId":"00910000-0000-4000-8000-000000000001","operationId":"synthetic-append-001","inventoryRevision":3,"collections":[{"collectionId":"00910000-0000-4000-8000-000000000011","version":2,"layoutRevision":1}],"commands":[{"kind":"insertAssign","collectionId":"00910000-0000-4000-8000-000000000011","slotId":"synthetic-new-slot","before":null,"target":null,"selection":{"kind":"existing","inventoryItemId":"synthetic-unassigned-copy","itemVersion":4}}]}
```

Normal inventory limits remain 100 commands, 32 collections, 256 selected affected entities, 256 KiB request and 1 MiB receipt. Insertion additionally caps a collection at 4,096 slots and total order work at 8,192 rows per request, counting the entire current order plus each new slot. Audit/recovery evidence retains the existing 16,384-entity/16 MiB bound. The 10-second deadline is unchanged. No truncation, chunked partial success or timeout increase is used; stale anchors/copies, collisions, allowance or recorder failures roll back the whole request.

One existing ledger receipt and one atomic history event cover the batch. Exact original replay precedes mutable reconstruction and cannot recreate a slot or copy after a later edit/recovery. Safe native recovery removes only the proved new slot/acquisition or returns the reused item to Unassigned; changed dependencies, layout or ABA reject. Restoring private asset metadata remains explicitly unsupported. A fresh preview decides support, not the insertion receipt. The original operation, slot and item IDs stay immutable through durable retry; only a separate fresh complete scoped read can acknowledge remote delivery. Public developer read pages cannot supply that snapshot.


The staged scanner now composes this existing operation with existing-slot assignments in one explicitly reviewed batch. Append choices create a free slot or exact card target with the selected Unassigned/new Raw copy; no separate slot-creation request is sent. Capture/current-grid/order/copy guards, real IDB commit and fresh complete-read ACK remain required. Capture and manual identity review are device UI, not a separate REST/MCP operation. Production routes remain disabled. See [scan review](/docs/scan-destinations).

### Prepared native recovery rejection

Native recovery remains staged and returns `503 native_operations_staged` before execution. The prepared v1/v2 apply contract declares REST `409 storage_recovery_rejected`, or MCP `isError:true`, only for a committed strict `error.rejection` containing `outcome:"rejected"`, the original `operationId`, known `code` and `inventoryRevision`. Codes are `recovery_plan_conflict` and `recovery_dependency_conflict`. Arbitrary 409/SQL errors, missing receipts, cancellation and billing/access errors are not noncommit proof. Exact accepted/rejected replay requires current authority and precedes mutable plan reconstruction.

In the staged app, durable proof permits a separately fresh complete current owner/session read and explicit **Discard noncommitted recovery**. Discard preserves original request/proof with a distinct discarded state, never accepted/synchronized. **Review new recovery** then needs a new preview and explicit confirmation with a new operation ID. Unknown and accepted requests never gain discard/rebase. The existing legacy Undo contract is unchanged; no private inverse, evidence, certificates or assets are exposed. This preparation is not an enabled capability or release announcement.


### Prepared creation and arrangement rejection

Creation and arrangement import remain staged with fixed `503 native_operations_staged` and zero executor calls. Migration 093 prepares permanent noncommit outcomes in their original lifetime ledgers. After admission, creation declares REST `409 storage_creation_rejected` and import `409 storage_import_rejected`; MCP uses `isError:true` with matching text/structured JSON. Strict `error.rejection` contains only `outcome:"rejected"`, the original `operationId`, known `code` and `inventoryRevision`. MCP accepted `outputSchema` excludes errors; `holofolder.com/errorSchemas` declares them separately.

Creation reasons are `inventory_revision_conflict` and `creation_identity_conflict`. Import reasons are `inventory_revision_conflict`, `inventory_collection_conflict`, `arrangement_destination_conflict` and `import_copy_conflict`. Only dedicated controlled engine predicates after rollback can commit proof. Ordinary 409/SQL errors, cancellation, audit or COMMIT failure, missing owner state, billing/access and unknown network outcomes remain unknown. Never infer noncommit from message text. Exact accepted/rejected replay follows current authority checks and precedes mutable reconstruction, even after later edits/deletion/recovery.

Future consumers must bind a trusted proof to the original family, immutable request and authenticated owner/session scope, then obtain a fresh authoritative complete current read and require explicit reconciliation before discard or review/confirmation of a new operation ID. A shape guard or matching ID alone does not authorize discard. Redacted developer reads are not complete-read authority. Creation/import durable client integration remains a separate gate; this contract does not enable a UI, safe client discard or customer availability. Existing legacy Undo is unchanged.
